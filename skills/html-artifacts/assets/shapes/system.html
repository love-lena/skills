How an offline reading pack is assembled

Three kinds of source material become one portable file. Parallel build steps converge on an assembler; every validation must pass before the pack reaches its reader.

Read the complete flow as text
  1. Markdown documents, diagram sources, and attachments enter a source snapshot. The snapshot records a manifest of pinned versions and required inputs.
  2. The manifest feeds the text builder, diagram renderer, and asset packager in parallel. All three outputs converge on the HTML assembler.
  3. The assembled file goes to the offline, contrast, and link checks in parallel. Each result goes to the release gate.
  4. All checks passing produces a reading pack, which is delivered to the reader. Any failure instead produces a findings report.
  5. The findings report returns to the manifest for revision and a new attempt. No partially validated pack is released.

The manifest holds the build together

Every branch uses the same pinned inputs. The manifest records source versions, required attachments, and the generated pack’s identity, so a retry cannot silently mix old text with new diagrams.

Parallel work has explicit join points

The assembler waits for text, diagrams, and packaged assets. The release gate waits for all three validation results. Arrows show dependencies; their placement does not imply that one parallel check runs before another.

Release rule: missing results count as incomplete. A failed or incomplete attempt produces findings, and cannot produce a delivered pack.

A delivered pack remains a snapshot

The file contains its reading resources and visible provenance. Editing a source requires a new build. Optional external references are labelled as requiring connectivity; required resources must work offline.
